# H3g — `norte help` in the CLI Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `norte help` reads the same corpus the TUI and the GUI show — index,
one topic, a search, the keyboard cheatsheet, and a `--json` dump for agents —
as plain text, embedded, with no daemon.

**Architecture:** A new `crates/norte-cli/src/help.rs` owns everything: a
`CliChords` resolver (the CLI's answer to the three questions `norte-help`
asks), a plain-text renderer over `norte_help::Block`, the search, and the JSON
projection. `main.rs` gains one `clap` subcommand that calls into it. The
keymap comes from the user's real config layers — the same ones `norte doctor`
reads — so the cheatsheet and the `{{cmd:…}}` marks name the keys this user
actually has.

**Tech Stack:** Rust 2024, `clap` (derive, as the rest of the CLI),
`norte-help` (corpus + model), `norte-frontend::keymap` (presets, layers,
`Effective`, `paint_chord`), `norte-i18n`, `serde_json` for `--json`,
`assert_cmd` for the CLI tests.

## Context an implementer needs before task 1

* `docs/superpowers/specs/2026-08-04-help-system-redesign-design.md`, section
  *Surfaces → CLI*. H3g is one row of its phase table; H3f (the GUI view) is its
  sibling and landed first — read `crates/norte-gui/src/help_view.rs` and
  `crates/norte-gui/src/help_render.rs`, which are the same two pieces for a
  frontend that paints. This plan deliberately repeats their SHAPE and shares
  nothing: the CLI has no keymap table, no plugin snapshot and no pane context,
  so a shared abstraction would be three optional parameters wide.
* `crates/norte-cli/src/doctor.rs::check_keymaps` — how the CLI already reads
  the user's keymap layers (`norte_config::standard_layers` →
  `norte_frontend::config::load_keymap_layer` → `Effective::build_for_subset`).
  Reuse that path; do not invent a second one.
* `crates/norte-cli/tests/smoke.rs` — the CLI test idiom (`assert_cmd`, a real
  tempdir, `NORTE_CONFIG_DIR` for isolation).

### Traps this phase walks into (all have drawn blood before)

* **A binary that panics on a closed pipe.** `println!` panics on
  `BrokenPipe`, so `norte help | head -5` would print a panic at the user.
  Task 5 handles it; the test pipes into a reader that closes early.
* **Stale CLI binary in an E2E.** `cargo nextest` rebuilds libs but not the
  `norte` binary — run `cargo build -p norte-cli` before re-running a failing
  CLI test, or you will debug the previous build.
* **Exit code after a pipe** is the LAST command's. Check `$status` without a
  pipe (or `grep -E '^error|Summary'` the log) before claiming a gate is green.
* **`items_after_test_module`**: in a binary crate, `#[cfg(test)] mod tests`
  must be the LAST item of the file.
* **Rustdoc public → private link** is a hard error in `just ci`'s `docs` step:
  name a private item in backticks, never in `[]`.

## Surface

```
norte help                      # the index page
norte help copying              # one topic by id
norte help keys                 # the effective-keymap cheatsheet
norte help --list               # every topic: id and title
norte help --search zip         # topics whose text, title, tags or commands match
norte help --json               # the whole corpus as JSON (for agents and goldens)
norte help copying --json       # one topic as JSON
```

Exit codes, following `grep` where it applies:

| situation | code | where the text goes |
| --- | --- | --- |
| page/list/search printed | 0 | stdout |
| `--search` with no matches | 1 | stderr, one line |
| unknown topic id | 1 | stderr, one line naming `--list` |
| reader closed the pipe | 0 | nothing |

## Out of scope, and why

* **Plugin pages.** Reaching them needs `PluginRegistry::discover` and a
  per-plugin `help.md` parse; `norte doctor` already reports what is wrong with
  one, and the two surfaces that show a plugin's page (TUI, GUI) both have a
  catalogue in hand. State it in the CHANGELOG rather than half-doing it.
* **Localizing `clap --help`** — out of scope by the 2026-07-23 design.
* **Colour.** The corpus carries structure, not style; plain text with a
  two-space indent reads the same in a pipe and in a terminal, and adding ANSI
  would mean adding a tty check and a `--color` flag for one page of prose.

```rust
/// The CLI's [`ChordResolver`]: the reader's chord, a short label, and — here
/// — "everything is available".
///
/// Availability is the one answer that differs from the other two frontends,
/// and it is a fact about this process rather than a shortcut: there is no
/// pane, no selection, no connection and no plugin catalogue, so every
/// impediment the shared table knows how to report is unknowable from here.
/// Dimming a row would be a claim; not dimming one is the absence of a claim.
/// `norte_frontend::availability::verdict` fails open for exactly this reason,
/// and this type simply does not consult it.
pub struct CliChords {
    /// Command to its painted chord, filled browse → viewer → dialog. First
    /// writer wins, so a command bound in several screens keeps the one that
    /// fires first — same precedence the TUI's resolver uses.
    chords: std::collections::HashMap<String, String>,
    /// The language `label` answers in.
    lang: Lang,
}

impl CliChords {
    /// Builds from the user's REAL keymap: the preset named in `norte.toml`
    /// plus every `keymap.toml` layer, exactly as `norte doctor` reads them.
    ///
    /// A layer that fails to parse is SKIPPED rather than fatal: this command
    /// prints documentation, and refusing to explain the app because a config
    /// file is broken is the least helpful moment to be strict. `norte doctor`
    /// is the command that reports it, and the page says which keys the
    /// surviving layers give.
    #[must_use]
    pub fn from_config(lang: Lang) -> Self {
        let layers = norte_config::standard_layers();
        let preset_name = norte_config::load(&layers)
            .map(|c| c.preset)
            .unwrap_or_else(|_| norte_config::DEFAULT_PRESET.to_owned());
        let mut sources = Vec::new();
        let mut layer_kfs = Vec::new();
        for (dir, kind) in &layers.dirs {
            if let Ok(Some(kf)) = norte_frontend::config::load_keymap_layer(dir, *kind, &mut sources)
            {
                layer_kfs.push(kf);
            }
        }
        Self::build(&preset_name, &layer_kfs, lang)
    }

    /// The same thing with no layers — the shape the tests pin, and the
    /// fallback when the config cannot be read.
    #[must_use]
    pub fn from_preset(preset: &str, lang: Lang) -> Self {
        Self::build(preset, &[], lang)
    }

    fn build(preset: &str, layers: &[norte_frontend::keymap::KeymapFile], lang: Lang) -> Self {
        use norte_frontend::keymap::{Effective, Screen, presets};

        let src = presets::source(preset)
            .or_else(|| presets::source(norte_config::DEFAULT_PRESET))
            .unwrap_or_default();
        let mut chords = std::collections::HashMap::new();
        if let Ok(preset_kf) = norte_frontend::keymap::parse_keymap(src) {
            for screen in [Screen::Browse, Screen::Viewer, Screen::Dialog] {
                // The command vocabulary comes from the PRESETS themselves:
                // the CLI has no `COMMANDS` table of its own, and inventing one
                // would be a third list to keep in sync with two frontends.
                let known: Vec<String> = norte_frontend::keymap::preset_commands(screen);
                let known: Vec<&str> = known.iter().map(String::as_str).collect();
                let Ok(eff) = Effective::build_for_subset(&preset_kf, layers, &known, screen) else {
                    continue;
                };
                for (seq, cmd) in eff.bindings() {
                    chords
                        .entry(cmd.to_owned())
                        .or_insert_with(|| norte_frontend::keymap::paint_chord(&seq));
                }
            }
        }
        Self { chords, lang }
    }

    /// Fluent id of a command's short label: `dialog.*` verbs live in
    /// `dialog-cmd-*` and everything else in `help-cmd-*` — routed by PREFIX
    /// and not by which list the caller is walking, because the `dialog`
    /// effective merges the preset's `[global]` section and would otherwise ask
    /// the wrong catalogue for `app.quit`.
    fn label_id(command: &str) -> String {
        if command.starts_with("dialog.") {
            format!("dialog-cmd-{}", command.replace('.', "-"))
        } else {
            format!("help-cmd-{}", command.replace('.', "-"))
        }
    }
}

impl ChordResolver for CliChords {
    fn chord(&self, command: &str) -> Option<String> {
        self.chords.get(command).cloned()
    }

    /// Blank on a miss, never the echoed id: `norte_i18n::t_in` answers a
    /// missing message with the id itself, and returning that would print
    /// `help-cmd-…` at the reader instead of letting
    /// `norte_help::render_command` fall back to naming the command.
    fn label(&self, command: &str) -> String {
        let id = Self::label_id(command);
        let text = norte_i18n::t_in(self.lang, &id);
        if text == id { String::new() } else { text }
    }

    fn availability(&self, _command: &str) -> Availability {
        Availability::Available
    }
}
```

Check the real names before writing: `norte_config::DEFAULT_PRESET` and
`Layers.dirs` are used by `doctor.rs::check_keymaps`, and
`norte_frontend::keymap::KeymapFile` must be public (it is — `doctor.rs` holds
a `Vec` of them). If `preset_commands` returns `Vec<String>`, keep the two-step
borrow above; a `&[&str]` built from a temporary will not compile.

Add `mod help;` to `main.rs`.

- [ ] **Step 3: Implement**

Emit, in this order (the same order the other two frontends use, so one page
reads the same on three surfaces):

1. the title;
2. a rule of `─` as wide as the title;
3. the plugin provenance line for `Origin::Plugin`, UNCONDITIONALLY — copy
   `crates/norte-gui/src/help_render.rs::plugin_badge`, including its
   `is_blank_id` guard on the publisher;
4. the blocks, blank line between them, in the closed vocabulary of
   `norte_help::Block` (`Heading`, `Paragraph`, `Bullets` with `• `, `Code`
   indented two spaces and NEVER wrapped, `Table` as aligned columns, `Callout`
   prefixed `note:`/`warning:`/`tip:` — ASCII words rather than the TUI's
   glyphs, because this stream may be a pipe into something that is not a
   terminal);
5. `norte_help::rows_of(topic, r)` as `  {chord:>10}  {label}`, and a row with
   no chord shows `—`;
6. `See also: <title>, <title>` from `see_also`, resolved through
   `norte_help::topic(lang, id)` with the id as fallback.

Inline spans go through `norte_help::render_span`, except `CommandRef`, which
must go through `norte_help::render_command` so a chord and a name stay
distinguishable (`CommandText::Chord` vs `Name`) — flattening them makes every
mark read as a key.

Return one `String`. No wrapping: the terminal wraps, and a wrapped line is a
lie in a pipe.

```rust
    // next write and print a Rust backtrace at the user.
    let mut child = Proc::new(assert_cmd::cargo::cargo_bin("norte"))
        .args(["help", "--json"])
        .env("NORTE_CONFIG_DIR", "/nonexistent-norte-config")
        .env("NORTE_LANG", "en")
        .stdout(Stdio::piped())
        .stderr(Stdio::piped())
        .spawn()
        .expect("spawn");
    // Read ONE byte, then drop the pipe.
    let mut buf = [0u8; 1];
    let _ = child.stdout.take().expect("stdout").read(&mut buf);
    let out = child.wait_with_output().expect("wait");
    let err = String::from_utf8_lossy(&out.stderr);
    assert!(
        !err.contains("panicked"),
        "a closed pipe must be a quiet exit, not a panic: {err}"
    );
}
```

Writing, and this is the whole pipe-safety fix:

```rust
/// Writes `text` to stdout, treating a closed pipe as a normal end.
///
/// `println!` PANICS on `BrokenPipe`, so `norte help | head -5` printed a Rust
/// backtrace at the reader — the pitfall this repo has already recorded once.
/// A reader that walked away is not an error: nothing is printed and the exit
/// code stays 0.
fn write_out(text: &str) -> ExitCode {
    use std::io::Write as _;
    let stdout = std::io::stdout();
    let mut lock = stdout.lock();
    match lock.write_all(text.as_bytes()).and_then(|()| lock.flush()) {
        Ok(()) => ExitCode::SUCCESS,
        Err(e) if e.kind() == std::io::ErrorKind::BrokenPipe => ExitCode::SUCCESS,
        Err(_) => ExitCode::FAILURE,
    }
}
```

* **Spec coverage.** The design's CLI block asks for index / one topic /

  corpus: tasks 2–5. Its test bullet ("`--json` golden; plain-output pipe

  the keys of the TUI/GUI, from a command that has none of its own. That is
  honest — the keymap is shared config, and the page says which app it is about
  — but if it reads as odd, the alternative is dropping `keys` from the CLI,
  not inventing a CLI keymap.
* **Deliberately not shared with the GUI's `help_render`.** The two differ in
  every decision that matters (wrapping, glyphs vs ASCII, roles vs none), and
  the GUI's lives in a crate outside the workspace, so the CLI cannot depend on
